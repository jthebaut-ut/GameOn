FANGEO — COMPLETE PUSH NOTIFICATION INFRASTRUCTURE AUDIT
Date: 2026-08-12
Scope: GameOn / FanGeo iOS + Supabase SQL + Edge Functions
Mode: READ-ONLY. No code changes, no migrations created, no deploy, no commit, no push.

This audit answers whether FanGeo should consolidate every notification
pipeline into one canonical infrastructure, and what that would take.


==============================================================================
EXECUTIVE SUMMARY
==============================================================================

FanGeo does NOT have one notification system. It has three overlapping
stacks plus several leftover one-off workers:

  A) Durable FanGeo Inbox  (fan_notification_inbox + live Action Needed queries)
  B) Server APNs workers   (~15 Edge functions, ~12 SQL queue helpers)
  C) iOS local notifications (GameReminderNotificationService — reminders,
     ratings, some pro-game cards)

A and B are intentionally independent (correct). The problem is that B is
not one worker: it is a family of near-copies that share some pieces
(_shared/apns_client.ts, authorizeSportsWorkerRequest) and bypass them in
others (Bearer-only SQL, local authorizeInvocation, a second ApnsClient
inside pro-game-score-alert-worker).

The last three production bugs (pickup change, team member-change, team
invitation) all failed at the SAME layer: SQL pg_net auth headers vs
hosted Edge secret class. Inbox succeeded; APNs never ran. That is the
clearest argument for consolidation.

Recommendation: YES, move to one canonical push + inbox backbone, in
PHASES. Do not rewrite every worker in one PR. First finish the auth
header cutover (the known 401 class), then extract a shared queue SQL
helper and a shared worker runtime. Keep notification-specific logic
as content/recipient/mute/deeplink plugins.

Current architecture is NOT maintainable long-term. Every new type
reimplements queue + auth + claim + token loop + copy + deeplink and
can silently ship the obsolete Bearer-only pattern.

  Inbox live  = FanGeo Inbox Action Needed projected from live domain rows

PART 3 — CANONICAL COMPONENTS
==============================================================================

1) One canonical APNs sender
   Status: MOSTLY CANONICAL
   Evidence: _shared/apns_client.ts used by invitation, pickup-change,
   member-change, member-left, deleted, friend, poke, chat, announcement,
   support-reply, awards.
   Exception: pro-game-score-alert-worker ships a second ApnsClient.
   Exception: iOS GameReminderNotificationService is a third sender
   (local, not APNs HTTP).

2) One canonical authorization helper
   Status: DUPLICATED / NEEDS CONSOLIDATION
   Shared: authorizeSportsWorkerRequest (correct: JWT Bearer, sb_secret
   apikey, cron). Used by the newer social/team workers.
   Legacy: local authorizeInvocation in
     notify-fangeo-announcement
     notify-support-reply
     notify-fangeo-plus-award
     notify-business-pro-award
     pro-game-score-alert-worker
   SQL not aligned: only 3 queues send dual-key (pickup, member-change,
   invitation-prepared). Chat/friend use XOR. Others Bearer-only.

3) One canonical token lookup
   Status: DUPLICATED
   Pattern is the same query copied everywhere:
     user_push_tokens where user_id in (...) and is_active = true
   Pickup-change uses list_pickup_game_change_push_tokens RPC instead
   (good for recipient rules, still a second access path).
   No shared TypeScript helper like loadActivePushTokens(admin, userIds).

4) One canonical queue format
   Status: NEEDS CONSOLIDATION
   Three header strategies, two Vault orderings, many body shapes:
     {update_event_id}
     {invitation_id, event_id, kind}
     {event_id}
     {message_id, message_source, chat_type}
     {friendship_id, event_id}
     {poke_id}
     {announcement_id}
     {conversation_id, message_id}
   push_worker_auth_headers (20260923) was an attempt at canonical
   headers but is XOR, not dual-key, and was not adopted by later
   team/pickup queues (they inlined dual-key instead).

5) One canonical inbox writer
   Status: MOSTLY CANONICAL WRITER, DUPLICATED SOURCES
   Writer: upsert_fan_notification_inbox is the only table writer.
   Fanout helpers: pickup, member-change, member-left.
   But Action Needed also merges LIVE domain queries (invites, friends,
   join approvals, ratings). That split is a product feature (durable
   vs pending-state), not a bug — but it is a second pipeline.

6) One canonical logging system
   Status: DUPLICATED
   Per-worker LOG_PREFIX strings. sportsWorkerAuthLog is shared for
   auth only. No shared delivery logger (token id, env, APNs status,
   reason, apns-id) — each worker copies the loop.

7) One canonical retry strategy
   Status: NEEDS CONSOLIDATION
   Only pickup_game_update_events has retryable +
   retry_pickup_game_change_push_notifications.
   Invitation/member-left/poke/friend/chat: fire-and-forget.
   A 401 leaves ledger=queued and never replays.

8) One canonical dedupe strategy
   Status: DUPLICATED
   Inbox: (user_id, deduplication_key) unique — good, but key recipes
   differ per fanout.
   APNs: one delivery table per worker (8+ tables).
   Pickup: fingerprint on event row.
   Invitation: event_id UUID generated per invite/resend.
   Chat: (message_id, recipient).
   No shared "exactly-once per (type, subject, recipient)" helper.

9) One canonical deep-link model
   Status: DUPLICATED
   Common idea: userInfo.source + entity ids. ~15 Swift files, each
   with its own keys (invitation_id vs pickup_game_id vs event_id vs
   friendship_id). No shared NotificationDeepLink protocol.
   Inbox destinations (teamsInvites, scheduleActivity, teamsHome, …)
   are a second mapping that must stay in sync with APNs custom data.

PART 4 — IDENTIFY FRAGILITY
==============================================================================

This is the production failure mode already proven three times:

  Inbox / domain write succeeds
    → queue runs
    → pg_net POSTs with a header the hosted Edge will not accept
    → 401 invalid_secret
    → token lookup never runs
    → APNs never sent
    → user sees Inbox, not iOS banner

Places a type can succeed while a sibling fails
(because it bypasses the common infrastructure):

A) SQL AUTH HEADERS (highest current risk)
   Dual-key (safe with shared authorizer):
     queue_pickup_game_change_push_notification          20260988
     queue_fan_team_member_change_push_notification_apns 20260990
     queue_fan_team_invitation_push_notification         20260993 PREPARED
   XOR (unsafe if Vault JWT and Edge only has sb_secret):
     queue_chat_message_push_notification                20260923
     queue_direct_message_push_notification              20260923
     queue_friend_request_push_notification              20260923
   Bearer-only (same invitation bug class):
     queue_profile_poke_push_notification                20260925
     queue_fan_team_member_left_push_notification_apns   20260957
     queue_fan_team_deleted_push_notification            20260945
     queue_support_reply_push_notification               20260832
     queue_fangeo_announcement_push_notification         20260834
     queue_fangeo_plus_award_push_notification           20260841
     queue_business_pro_award_push_notification          20260842

B) EDGE AUTH IMPLEMENTATION
   Shared authorizer: invitation, pickup-change, member-change,
   member-left, team-deleted, friend, poke, chat handler.
   Local Bearer==SERVICE_ROLE_KEY: announcement, support-reply,
   plus-award, business-pro-award, pro-game-score-alert-worker.
   Dual-key SQL cannot save a worker that never reads `apikey`.

C) VAULT SECRET NAME / ORDER
   Safe order (fangeo_service_role_key first): 88, 90, 93.
   Unsafe order (SUPABASE_SERVICE_ROLE_KEY first): 42, 45, 57, 25,
   older announcement/support/award queues.
   If Vault SUPABASE_SERVICE_ROLE_KEY was rotated to sb_secret_* and
   fangeo_service_role_key still holds the JWT, Bearer-only + first-match
   can send the wrong class.

D) QUEUE PAYLOAD SHAPES
   Each worker parses a different JSON body. A shared retry cron cannot
   blindly re-POST without a common envelope
   ({ worker, event_id, payload }).

E) TOKEN QUERIES
   Most: is_active + user_id.
   Pickup-change: dedicated RPC (correct for membership/invite rules).
   Join decisions: targeted ids, skip mute.
   Inconsistency is OK for recipient RULES, not for the token table
   access itself (should be one helper).

F) APNs ENVIRONMENT
   Shared client uses token.environment (sandbox|production) per row.
   Local pro-game client + iOS local notifications can disagree with
   that mapping. Stale active tokens still 200 from APNs.

G) LOGGING
   Cannot grep one prefix for "all APNs 401s". Invitation logs
   [FanTeamInvitationPush], pickup [PickupGameChangePush], etc.
   Auth failures look the same but live in different function logs.

H) RETRY
   Pickup can be replayed. Invitation/member-left/poke cannot.
   After a platform auth outage, only pickup heals.

I) DEDUPE
   Re-invite vs resend vs edit fingerprint vs message id — all custom.
   Risk of duplicate APNs if a worker is retried without claim, or
   missed APNs if claim treats queued as already_claimed (invitation
   specifically treats queued as claimable — good and unique).

J) INBOX vs APNs COVERAGE
   Types with Inbox but no APNs: pickup invite, join request (organizer),
   ratings (local only), friend accept (neither), team invite accept.
   Types with APNs but no durable inbox: chat, poke (mostly live),
   team deleted, awards, announcements, support reply, pro-game.
   Users experience "sometimes Inbox, sometimes banner, sometimes both,
   sometimes neither" depending on type — not a single product rule.

K) iOS LOCAL vs SERVER
   Ratings and some live-game alerts can appear from local scheduling
   even when the server worker is down — and can miss when the app
   never ran. Do not use local notifications as a workaround for
   social APNs (standing product rule).

PART 5 — RECOMMENDED ARCHITECTURE
==============================================================================

Do not merge all Edge functions into one mega-function in a single
cutover. Keep thin worker entrypoints (or one worker with a type
switch) but share EVERYTHING below the type plugin.

Target:

  Business event (RPC / trigger)
       │
       ▼
  Canonical emit_notification_event(type, payload, recipients, ...)
       │  writes notification_events (one table)
       │
       ├──────────────────────────────┐
       ▼                              ▼
  Canonical inbox fan-out        Canonical push enqueue
  upsert_fan_notification_inbox  queue_notification_push
  (skip if type is live-only     (always dual-key headers
   Action Needed: invites,        + fangeo_service_role_key first
   friend requests, ratings)      + both cron header names)
       │                              │
       ▼                              ▼
  FanGeo Inbox                   pg_net → notify-fangeo-push
  Action Needed | Notifications       │
                                      ▼
                               authorizeSportsWorkerRequest
                                      │
                                      ▼
                               load plugin(type)
                                 recipients (if not already snapshotted)
                                 title/body
                                 deep-link custom data
                                 mute / prefs
                                 inbox category (already written)
                                 dedupe key
                                      │
                                      ▼
                               loadActivePushTokens(userIds)
                               ApnsClient.send (shared only)
                                      │
                                      ▼
                               delivery_log
                                 (event_id, user_id, token_id, env,
                                  http_status, apns_reason, apns_id)
                               retry if retryable (auth/network/5xx)
                               do not retry 410/Unregistered (invalidate)

Notification-specific plugin fields ONLY:
  - recipients
  - title / body
  - deep-link
  - mute rules
  - notification category (Action Needed vs Notifications vs chat-only)
  - dedupe key

Shared, never reimplemented:
  - Vault lookup + dual-key headers
  - worker auth
  - token load + environment routing
  - APNs client
  - delivery claim
  - structured logs
  - retry cron
  - inbox upsert

Live Action Needed types (team invite, pickup invite, friend request,
join approval, pending rating) should KEEP querying live domain state
for the card (so accept/decline/expiry disappear immediately). They
may ALSO write a durable Notifications-tab history row if product
wants history, but APNs must still go through the canonical queue.

Chat should stay on the same auth/token/APNs/retry backbone even if
it does not write fan_notification_inbox (chat unread is the inbox).

Pro-game / live scores can stay a separate *content* plugin but MUST
drop the local ApnsClient and local authorizeInvocation.

iOS local notifications remain valid for TIME-BASED reminders
(kickoff in 30 minutes) that cannot wait for a server event. They
must not replace server APNs for social/team/pickup events.

PART 6 — RISK ANALYSIS
==============================================================================

Implementation difficulty: MEDIUM–HIGH
  Not because APNs is hard — because there are ~15 workers, ~12 queues,
  ~8 delivery tables, and two inbox sources. The shared pieces already
  exist (ApnsClient, authorizer, inbox upsert). The work is mechanical
  alignment plus careful recipient/copy tests.

Regression risk: HIGH if done as one rewrite
  Chat volume is high; a shared worker bug would silence DMs, group
  chat, team chat, pickup chat at once. Pickup/team schedule already
  shares one worker — that concentration already bit copy/recipient
  bugs. Auth-header-only changes are LOW risk (proven by 88/90/93).

Rollout strategy: MULTIPLE PHASES (required)

  Phase 0 — Stop the bleeding (days)
    Apply prepared 20260993 (invitation dual-key) + redeploy
    notify-fan-team-invitation.
    Forward-migrate member-left, team-deleted, poke to dual-key
    (same SQL pattern as 88/90/93). Do not touch copy or recipients.
    Redeploy those three Edge functions only if comments/auth import
    need confirming they already use authorizeSportsWorkerRequest
    (member-left, deleted, poke already do).

  Phase 1 — Remaining SQL headers (1 week)
    Chat + friend: change push_worker_auth_headers to dual-key
    (Bearer AND apikey) OR stop using it and inline dual-key.
    Announcement / support-reply / awards: dual-key SQL + migrate
    those Edge functions from authorizeInvocation to
    authorizeSportsWorkerRequest. Do not weaken auth.

  Phase 2 — Shared SQL queue primitive (1–2 weeks)
    CREATE queue_fangeo_push(p_function text, p_body jsonb, ...)
    that owns Vault + dual-key + cron headers + request_id.
    Thin wrappers keep current function names so RPCs do not change.
    One migration; no behavior change if bodies/URLs stay identical.

  Phase 3 — Shared worker runtime (2–3 weeks)
    Extract loadActivePushTokens, claimDelivery(generic table or
    one delivery_log), sendToTokens, sportsWorkerAuthLog+delivery log.
    Point existing workers at the helpers WITHOUT merging them yet.
    Delete pro-game local ApnsClient.

  Phase 4 — Optional single worker (later)
    notify-fangeo-push with type switch + plugins.
    Keep old function URLs as 3-line adapters (like notify-direct-message)
    so SQL does not have to move in the same deploy.

  Phase 5 — Product coverage (separate, optional)
    Decide which gaps are product vs bugs:
      pickup invite APNs
      organizer join-request APNs
      friend accepted APNs
      team invite accepted APNs
      mentions
    Each is a plugin + inbox rule, not a new pipeline.

Do NOT combine Phase 0/1 with copy/deeplink/inbox redesigns.
That is how the last regressions happened.

Estimated effort
  Phase 0:  0.5–1 day remaining (93 apply + 3 sibling dual-key migrations)
  Phase 1:  2–4 days
  Phase 2:  3–5 days
  Phase 3:  1–2 weeks
  Phase 4:  1 week (optional)
  Phase 5:  product-driven
  Tests:    Deno auth/header/copy tests per worker + iOS Debug only if
            deeplink keys change (they should not in 0–3)

App rebuild: NO for phases 0–3 if custom data keys stay stable.


==============================================================================
PART 7 — FINAL RECOMMENDATION
==============================================================================

1) Should FanGeo move to one canonical notification infrastructure?

   YES — incrementally. The destination is one emit → inbox + queue →
   one authorizer → plugin copy → one ApnsClient → one delivery log.
   The destination is NOT "one giant Edge file next week."

2) Is the current architecture maintainable long-term?

   NO. It is already producing the same production defect on every
   worker that still uses Bearer-only SQL or local Edge auth. Adding
   "one more notify-*" will copy the obsolete pattern unless a shared
   queue primitive exists. Pickup-change is already a mega-worker
   carrying pickup edits, team schedule, announcements, and join
   decisions — that is consolidation without a plugin boundary, which
   is the wrong kind of consolidation (high coupling, shared failure).

3) Biggest weaknesses today

   - Three SQL auth header dialects (dual-key / XOR / Bearer-only)
   - Two Edge auth implementations (shared vs local compare)
   - Two Vault secret orderings
   - Retry only on pickup
   - 401s leave queued rows that never replay
   - Two inbox sources (table vs live) undocumented as a platform rule
   - Second ApnsClient in pro-game-score-alert-worker
   - ~10 cron secrets and ~8 delivery tables
   - Coverage holes: pickup invite, join-request-to-organizer, friend
     accept, team invite accept, mentions — look like "notification
     types" in the product but are not on the APNs bus
   - iOS local ratings/reminders can be mistaken for APNs success

4) Biggest benefits of consolidation

   - One place to fix auth (the last three P0s disappear as a class)
   - One retry/ops story after Edge or APNs outages
   - One log query for "did this user get a banner"
   - New types become a plugin (recipients + copy + deeplink + mute)
     instead of a new migration + new Edge function + new Swift file
     + new cron secret
   - Inbox and APNs stay independent (already correct) but both are
     invoked from the same emit helper so one cannot be forgotten
   - Dual-key + shared authorizer stays fail-closed (no weaker auth)

5) Would this reduce future notification bugs?

   YES for infrastructure bugs (auth, tokens, environment, retry,
   "Inbox worked but no banner").
   PARTIALLY for product bugs (wrong recipients, wrong copy, wrong
   mute). Those stay in plugins and still need tests — but they stop
   being blocked by a 401 that looks like a token problem.

  does not use list_pickup_game_change_push_tokens, so it skips that

  not the same safety net as the default roster path.

E6. notify-pickup-game-change log uses auth.source
  index.ts ~667 interpolates auth.source while the in-scope result is
  invocation. That log line can throw after a successful send.
  Not an APNs-delivery bug; it is a worker-runtime footgun.

E7. 20260923 restored the DM Edge URL
  queue_direct_message_push_notification POSTs notify-direct-message
  (compat adapter). queue_chat_message_push_notification POSTs
  notify-chat-message. Both share chat_message_push_handler.ts.
  XOR push_worker_auth_headers still applies to both.

  Always suppress banner: team_invitation, team_deleted,

  Conditional: chat_message only if that conversation is already open.

  Inbox ingest skips Action Needed sources so they never land on the
  Notifications tab: team_invitation, friend_request, pickup invite,
  pickup_creator_rating, join_request.

E9. No UNNotificationCategory
  Zero setNotificationCategories / actionable Accept-Decline buttons.
  All interaction is tap → deep link.

E10. Local reminder deep-link holes
  Venue “Game starting soon” (fangeo.gameReminder.) has no source key.
